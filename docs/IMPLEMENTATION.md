## 01 Як працювати з Opus

1. Відкрити теку проєкту в Claude Code, обрати модель Opus. Файл `CLAUDE.md` у корені підхоплюється автоматично — у ньому короткі правила та посилання на цей документ.
2. **Один етап — одна сесія.** Етапи описано в розділі 10. Не просити «зроби все одразу»: контекст розмивається, а помилки ранніх етапів множаться.
3. Шаблон запиту на початку кожної сесії:

   ```
   Прочитай docs/IMPLEMENTATION.md. Реалізуй етап N повністю.
   Дотримуйся розділів 02–09 як джерела істини. Наприкінці пройди
   всі критерії приймання етапу N і покажи результат кожної перевірки.
   Якщо специфікація суперечить реальності (версія бібліотеки, формат даних) —
   зупинись і скажи, не вигадуй обхідних рішень мовчки.
   ```

4. Після кожного етапу: самому запустити команди з критеріїв приймання, зробити коміт (`git commit`), лише тоді починати наступний.
5. Якщо під час етапу змінилося архітектурне рішення — попросити Opus оновити цей документ у тому самому коміті, щоб наступні сесії бачили актуальний стан.
6. Перед етапом 0 виконати `git init` у корені.

## 02 Архітектура та зв'язки

### Сервіси

| Сервіс | Де працює | Порт | Залежить від |
|---|---|---|---|
| `web` | Docker, Next.js | 3000 | `api` |
| `api` | Docker, FastAPI (uvicorn) | 8000 | `db`, Ollama |
| `db` | Docker, образ `pgvector/pgvector:pg17` | 5432 | — |
| Ollama | нативно на Windows-хості | 11434 | — |

Ollama свідомо не в Docker: на Windows нативний застосунок простіше отримує доступ до GPU. Контейнер `api` звертається до нього через `http://host.docker.internal:11434` (у `docker-compose.yml` для `api` додати `extra_hosts: ["host.docker.internal:host-gateway"]`).

### Правила взаємодії

- Браузер знає лише про `web`. У `next.config.ts` налаштовано `rewrites`: `/api/:path*` → `${API_INTERNAL_URL}/:path*`. Завдяки цьому немає CORS, а cookie сесії — first-party. `rewrites()` обчислюється під час `next build`, тому `API_INTERNAL_URL` передається в образ `web` як build-arg (і ще раз як змінна середовища для серверних `fetch`).
- `api` — єдиний, хто має доступ до бази та Ollama. Фронтенд ніколи не викликає Ollama напряму.
- Важкі обчислення (навчання ALS, побудова ембедингів, оцінювання) — це **офлайн-скрипти** в `backend/scripts/`, які запускаються вручну через `docker compose exec api python -m scripts.<name>`. Онлайн-частина `api` лише читає готові артефакти.
- Артефакти ALS: `/app/artifacts/als_{domain}.npz` (фактори користувачів і об'єктів) + `als_{domain}_maps.json` (відповідність індексів матриці та `id` у базі). Завантажуються в пам'ять у `lifespan` FastAPI (`app.state.als_models`); є адмін-ендпоінт для перезавантаження без рестарту.
- Томи Docker — лише іменовані: `pgdata` (Postgres), `rawdata` → `/app/data` (сирі датасети, кеш Open Library), `artifacts` → `/app/artifacts` (моделі, результати оцінювання). **Bind-монтувань теки проєкту немає й не додавати**: шлях проєкту містить теку з довгою кириличною назвою (> 255 байт у UTF-8), і Docker Desktop падає з `file name too long`. Код вшивається в образ; у розробці його синхронізує `docker compose watch` (секція `develop.watch` у compose). Файли з тома дістаються командою `docker compose cp api:/app/artifacts/... <куди>`.
- Порти хоста задаються в `.env` (`WEB_HOST_PORT`, `API_HOST_PORT`, `DB_HOST_PORT`), бо на машині розробника стандартні порти можуть бути зайняті іншими проєктами.

### Потік запиту «мої рекомендації»

```
GET /api/recommendations?domain=movie
 1. api: зчитати оцінки та перегляди користувача з БД
 2. ALS-кандидати (top-200)            ─┐
 3. контентні кандидати (pgvector, 200) ─┴─► злиття → top-30
 4. перевірити кеш LLM (ключ: user + хеш оцінок + domain)
      є  → віддати top-10 з поясненнями
      ні → віддати гібридний top-10 одразу (explanation = null),
           клієнт окремо викликає POST /api/recommendations/explain
 5. explain: Ollama /api/chat → JSON → перевірка → запис у кеш → відповідь
```

Розділення на два запити потрібне, щоб сторінка відкривалася миттєво, а пояснення довантажувалися (генерація займає 5–40 с залежно від заліза).

Розширення: `CREATE EXTENSION IF NOT EXISTS vector;` (перша міграція Alembic).

| Поле | Тип | Примітка |
|---|---|---|
| id | bigserial PK | |

| password_hash | text, nullable | argon2 |
| display_name | text | |
| source | text | `web` \| `movielens` \| `bookcrossing` |
| external_id | text, nullable | id у вихідному датасеті; unique разом із `source` |
| created_at | timestamptz | |

**items**

| Поле | Тип | Примітка |
|---|---|---|
| id | bigserial PK | |
| domain | text | `movie` \| `book` |
| source | text | `movielens` \| `bookcrossing` |
| external_id | text | movieId або ISBN; unique разом із `source` |
| title | text | |
| year | int, nullable | |
| creators | text[] | автори книги; для фільмів порожньо |
| genres | text[] | жанри фільму / тематики книги |
| description | text, nullable | анотація (Open Library) |
| cover_url | text, nullable | |
| meta | jsonb | теги, видавець, imdbId/tmdbId тощо |

| rating_avg | real | у шкалі 1–10 |

Індекси: `(domain, rating_count DESC)`; GIN на `genres`; HNSW `USING hnsw (embedding vector_cosine_ops)`; для пошуку за назвою — `pg_trgm` GIN на `title`.

**ratings**

| Поле | Тип | Примітка |
|---|---|---|
| user_id | FK users | PK (user_id, item_id) |
| item_id | FK items | |
| value | smallint | **єдина шкала 1–10** (MovieLens ×2) |
| implicit | boolean | true для неявних взаємодій Book-Crossing (оцінка 0), тоді value = NULL |

**llm_cache** — `id`, `user_id`, `domain`, `profile_hash` (sha256 від відсортованих оцінок користувача + версії промпту + назви моделі), `payload` jsonb (впорядкований список `item_id` + пояснення), `created_at`. Unique `(user_id, domain, profile_hash)`.

## 04 Дані: завантаження та підготовка

### MovieLens

- Розробка: `ml-latest-small` (≈100 тис. оцінок, ≈9,7 тис. фільмів). Експерименти: `ml-1m`. Скрипт приймає `--variant`.
- Варіанти імпортуються в окремі бази: їхні ID користувачів не узгоджені. У `items.meta.dataset_variant` зберігається варіант, і повторний імпорт іншого варіанта в ту саму базу відхиляється.
- Формати різні: `ml-latest-small` — CSV із заголовками (`ratings.csv`, `movies.csv`, `tags.csv`, `links.csv`); `ml-1m` — файли `.dat` з роздільником `::`, кодування latin-1, тегів немає.
- Рік — із назви за шаблоном `(\d{4})` наприкінці; у `title` зберігати без року.
- Жанри розділені `|`; значення `(no genres listed)` → порожній масив.
- Теги користувачів (де є) агрегувати по фільму: до 15 найчастіших у `meta.tags`.
- Оцінка 0.5–5 → `value = round(rating * 2)`; `rated_at` із `timestamp`.
- Анотацій сюжету в MovieLens немає. Текст для ембединга будується з назви, року, жанрів і тегів. Це обмеження слід зазначити в дипломі; збагачення через TMDB — необов'язкове розширення, не входить в обсяг.

### Book-Crossing

- Станом на 17.11.2026 офіційне завантаження з університетського сервера недоступне. Узгоджене джерело для `download_data` — сирі `BX-Books.csv.gz`, `BX-Book-Ratings.csv.gz`, `BX-Users.csv.gz` з `https://github.com/zheng-da/BookCrossing`, коміт `b21eb595d30bb0a9cda840be937af02b9b7bfa77`. Виправлений CSV та готові підвибірки не використовуються. URL і коміт записуються поруч із даними в `*.source.json`. Підтримується також локальний оригінальний `/app/data/BX-CSV-Dump.zip` або `--bookcrossing-url`; `--bookcrossing-source official` явно обирає старе джерело.
- Файли `BX-Books.csv`, `BX-Book-Ratings.csv`, `BX-Users.csv`: роздільник `;`, кодування latin-1, лапки `"`, трапляються зламані рядки (читати з `on_bad_lines="skip"`, порахувати й вивести кількість пропущених).
- Реалізація використовує еквівалентний callback `on_bad_lines`, щоб рахувати відкинуті рядки. Невалідні оцінки, відсутні користувачі/книги та порожні назви також враховуються у `skipped`; дублікати — у `duplicates`, взаємодії поза k-core — у `filtered`. Фільтрація виконується після нормалізації ISBN та видалення дублікатів пар користувач–книга.
- ISBN нормалізувати: верхній регістр, прибрати все, крім цифр і `X`.
- Оцінка 0 означає неявну взаємодію → `implicit = true`, `value = NULL`. Оцінки 1–10 — як є.
- Фільтрація ядра (k-core, повторювати до стабілізації): книги з ≥ 10 взаємодіями, користувачі з ≥ 5 взаємодіями. Імпортувати лише те, що лишилося. Очікувано — кілька тисяч книг; точні числа вивести в лог і використати в дипломі.
- Часових міток немає — це впливає на спосіб розбиття (розділ 09).

Імпорт кожного датасету — одна транзакція. Повторний запуск оновлює записи за унікальними ключами, не дублюючи їх; повторний Book-Crossing не стирає анотації та тематики з Open Library. Агрегати перераховуються після імпорту: `rating_count` рахує всі взаємодії, `rating_avg` усереднює лише явні оцінки (0, якщо їх немає).

### Open Library

- Збагачуються лише книги, що пройшли фільтрацію.
- Запит: `GET https://openlibrary.org/api/books?bibkeys=ISBN:<isbn>,ISBN:<isbn>...&format=json&jscmd=details` — пакетами до 50 ISBN. Беруться `description` (може бути рядком або об'єктом `{value}`), `subjects`.
- Обкладинка: `https://covers.openlibrary.org/b/isbn/<isbn>-M.jpg?default=false` (зберігати лише URL; `default=false` дає 404 замість заглушки).
- Ввічливість: пауза ≥ 1 с між пакетами, заголовок `User-Agent` із назвою застосунку, повтор із затримкою при 429/5xx.
- Кеш сирих відповідей на диску (`data/openlibrary_cache/`), щоб повторний запуск не ходив у мережу. Скрипт має бути ідемпотентним і відновлюваним.
- Для книг без анотації ембединг будується з назви, автора, видавця й тематик.

### Текст для ембединга

Один шаблон для обох доменів (функція `build_item_text` у `app/recsys/content.py`):

```
Тип: фільм | книга
Назва: ...
Рік: ...
Автори: ...            (лише книги)
Жанри/тематики: ...
Теги: ...              (якщо є)
Опис: ...              (якщо є, обрізати до ~1500 символів)
```

Порожні рядки пропускаються. Шаблон англійською (дані англомовні): `Type: movie`, `Title: ...` тощо. Для книги додається `Publisher: ...`, якщо видавець є в `meta.publisher` — це забезпечує описаний вище резервний текст для книг без анотації.

### Побудова ембедингів

- `POST {OLLAMA_BASE_URL}/api/embed`, тіло `{"model": "bge-m3", "input": [<тексти>]}`, відповідь `{"embeddings": [[...], ...]}`. Пакети по 32.
- Вектори L2-нормалізувати перед записом.
- Обробляти лише `WHERE embedding IS NULL` (відновлюваність), показувати прогрес.
- HNSW-індекс створювати після масового заповнення.
- `scripts.build_embeddings` зберігає кожен пакет в окремій транзакції; розмірність, кількість, скінченність і ненульова норма векторів перевіряються до запису. Проміжні помилки не втрачають уже записаних пакетів. Параметри: `--domain movie|book`, `--batch-size 1..32`, `--limit N`.
- Міграція `0003_content_invalidation` створює тригер: зміна полів тексту (включно з `meta.tags` і `meta.publisher`) скидає `embedding` у NULL. Зміна оцінок, обкладинки чи службових метаданих вектор не скидає. Перед записом скрипт повторно перевіряє текст під блокуванням рядка, щоб не записати вектор застарілої версії опису.
- Індекс `ix_items_embedding_hnsw` описано в метаданих SQLAlchemy, а фізично його створює скрипт після того, як у всьому каталозі не залишилося NULL-векторів. Після цього `alembic check` не повинен знаходити розбіжностей. На порожній/частково заповненій БД відсутність цього відкладеного індексу до запуску скрипта очікувана.
- Побудова HNSW виконується з локальними `max_parallel_maintenance_workers=0` і `maintenance_work_mem=256MB`: однопроцесна побудова не перевищує стандартний ліміт Docker `/dev/shm=64MB` через паралельну shared-memory алокацію. Це не змінює глобальні налаштування PostgreSQL або Docker.

## 05 Рекомендаційні моделі

Домени `movie` і `book` мають різних користувачів, тому колаборативні моделі навчаються **окремо для кожного домену**. Простір ембедингів спільний — це дає змогу робити міждоменні рекомендації («книги для того, хто любить ці фільми») суто контентною моделлю; це необов'язкове розширення і хороший пункт для розділу про перспективи.

Єдиний інтерфейс для всіх моделей:

```python
class Recommender(Protocol):
    def recommend(self, user: UserHistory, k: int, exclude: set[int]) -> list[tuple[int, float]]:
        """Повертає (item_id, score), відсортовані за спаданням score."""
```

`UserHistory` — оцінки (item_id, value | None, implicit) і перегляди користувача. Модель не ходить у базу сама: історію їй передають. Це дозволяє в оцінюванні підставляти навчальну частину історії.

### Популярність (базова лінія)

Оцінка об'єкта — кількість позитивних взаємодій у навчальній вибірці. Не персоналізована.

### Контентна модель

- Профіль користувача: `p = normalize(Σ wᵢ · eᵢ)`, де `eᵢ` — ембединг об'єкта, `wᵢ = (value − 5.5) / 4.5` для явних оцінок (діапазон −1…1, негативні оцінки відштовхують профіль), `wᵢ = 0.3` для неявних взаємодій і переглядів.
- Якщо сума ваг позитивних об'єктів дорівнює нулю (усі оцінки низькі) — модель повертає порожній список, гібрид спирається на інші джерела.
- Онлайн: `SELECT id, 1 - (embedding <=> :p) AS score FROM items WHERE domain = :d AND id <> ALL(:exclude) ORDER BY embedding <=> :p LIMIT :k`.
- Офлайн (оцінювання): ембединги домену завантажуються в NumPy-матрицю, оцінка — скалярний добуток. Результат має збігатися з SQL-варіантом (тест).
- Схожі об'єкти для сторінки картки — той самий запит із вектором об'єкта замість профілю.
- Онлайн-пошук використовує HNSW (`ef_search=200`, `iterative_scan=strict_order`, pgvector ≥ 0.8); при відсутності індексу PostgreSQL виконує точний пошук. Для перевірки математичної еквівалентності й експериментів `SqlContentRecommender(exact=True)` вимикає індексний пошук лише на час запиту: HNSW за своєю природою наближений. Точний SQL та NumPy повинні давати однаковий top-10, з похибкою оцінок ≤ 1e-6. При однакових оцінках порядок визначає ID.
- `UserHistory` та `HistoryRating` оголошено в `app/recsys/types.py`. Уже оцінені/переглянуті об'єкти виключаються з результату. Повторні перегляди враховуються один раз; явна оцінка замінює слабкий сигнал перегляду того самого об'єкта. Для порожньої історії, відсутніх векторів або лише негативних оцінок повертається порожній список.

### Колаборативна модель (ALS)

- Бібліотека `implicit`, клас `implicit.als.AlternatingLeastSquares` (CPU).
- Матриця `user × item` у форматі CSR. Значення — довіра: `c = 1 + 4 · (value / 10)` для явних оцінок ≥ 6; `c = 1` для неявних; оцінки < 6 у матрицю не потрапляють (для ALS на неявному зворотному зв'язку вони не є позитивним сигналом).
- Початкові гіперпараметри: `factors=64`, `regularization=0.05`, `iterations=20`, `random_state=42`. Підбір — у розділі 09.
- Перед навчанням обмежити потоки BLAS: `threadpoolctl.threadpool_limits(1, "blas")` (інакше `implicit` попереджає і працює повільно).
- Користувачі з датасету: `model.recommend(user_idx, user_items[user_idx], N=k, filter_already_liked_items=True)`.
- **Користувачі платформи** (їх не було під час навчання): побудувати рядок CSR з їхніх оцінок і викликати `model.recommend(0, row, N=k, recalculate_user=True)` — фактор користувача обчислюється на льоту з наявних факторів об'єктів. Перенавчання не потрібне.
- Якщо в користувача менше ніж 1 позитивна взаємодія в домені — ALS повертає порожній список.

### Гібрид

1. Узяти по 200 кандидатів від ALS і контентної моделі, об'єднати множини.
2. Оцінки кожної моделі нормалізувати min-max у межах її списку кандидатів; відсутній у списку об'єкт отримує 0.
3. `score = α · als + (1 − α) · content`.
4. α залежить від кількості позитивних взаємодій користувача `n` у домені: `α = α_max · min(1, n / n_full)`. Початково `α_max = 0.7`, `n_full = 20`; обидва параметри підбираються на валідації. При `n = 0` працює лише контент, а якщо й профілю немає — популярність.
5. Реалізувати також злиття рангів RRF (`Σ 1 / (60 + rank)`) як альтернативу для порівняння в експериментах — це одна додаткова функція.

Холодний старт нового користувача: при реєстрації пропонується оцінити кілька популярних об'єктів із різних жанрів (онбординг); доки оцінок немає — показується популярне.

## 06 Мовна модель (Ollama)

### Клієнт

`app/llm/client.py` — тонка асинхронна обгортка над `httpx.AsyncClient` з двома методами: `embed(texts)` і `chat_json(messages, schema)`. Таймаут читання 120 с. Окремих SDK не потрібно.

Запит на генерацію:

```json
POST {OLLAMA_BASE_URL}/api/chat
{
  "model": "qwen3:8b",
  "stream": false,
  "think": false,
  "format": { ...JSON Schema відповіді... },
  "options": { "temperature": 0.3, "num_ctx": 8192 },
  "messages": [ {"role": "system", "content": "..."}, {"role": "user", "content": "..."} ]
}
```

- `format` із JSON Schema змушує модель повертати структурований JSON (текст у `message.content`).
- `think: false` вимикає режим міркувань Qwen3: відповідь у рази швидша, а для переранжування цього достатньо. Під час реалізації перевірити за актуальною документацією Ollama, що параметр підтримується встановленою версією; якщо ні — додати `/no_think` у кінець повідомлення користувача та вирізати блок `<think>…</think>` із відповіді.

### Завдання моделі

Вхід: профіль смаків + 30 кандидатів гібрида. Вихід: 10 обраних кандидатів у порядку релевантності з поясненням кожного.

Профіль у промпті (компактно, щоб уміститися в контекст):

- до 15 об'єктів із найвищими оцінками (назва, рік, жанри, оцінка);
- до 5 об'єктів із найнижчими оцінками;
- до 10 останніх переглядів;
- найчастіші жанри користувача.

Кандидати: порядковий номер `n` (1…30), назва, рік, жанри, перші ~200 символів опису. **У промпт передаються номери, а не id з бази** — малі числа модель плутає рідше; зворотне зіставлення робить код.

Системний промпт (суть): ти — рекомендаційний асистент; обирай лише з наданого списку; не вигадуй фактів про твори, спирайся тільки на надані поля; пояснення — 1–2 речення українською, з посиланням на конкретні вподобання користувача («ви високо оцінили …»); не згадуй номери кандидатів у тексті.

Схема відповіді:

```json
{
  "type": "object",
  "properties": {
    "recommendations": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "n": { "type": "integer" },
          "explanation": { "type": "string" }
        },
        "required": ["n", "explanation"]
      }
    }
  },
  "required": ["recommendations"]
}
```

### Перевірка відповіді та відмовостійкість

Код не довіряє моделі:

1. Розібрати JSON; відкинути елементи з `n` поза діапазоном, дублікати, порожні пояснення.
2. Якщо валідних менше 10 — доповнити наступними за гібридним рейтингом (без пояснення).
3. Якщо JSON не розбирається — одна повторна спроба; далі — гібридний порядок без пояснень.
4. Якщо Ollama недоступний або таймаут — те саме, плюс запис у лог. Користувач бачить рекомендації завжди.

Кешування: результат пишеться в `llm_cache`; ключ змінюється, коли користувач додає або змінює оцінку, тому нові пояснення генеруються лише після зміни профілю.

## 09 Наукове оцінювання

Скрипт `scripts/evaluate.py` + модулі `app/recsys/splits.py` і `app/recsys/metrics.py`.

### Розбиття даних

- **MovieLens** (є час): для кожного користувача взаємодії сортуються за часом; останні 10 % — тест, попередні 10 % — валідація, решта — навчання. Це імітує реальний сценарій «передбачити майбутнє за минулим».
- **Book-Crossing** (часу немає): випадкове розбиття по користувачу 80/10/10 із фіксованим `seed=42`.
- У тест потрапляють лише користувачі, які мають ≥ 1 релевантний об'єкт у тесті та ≥ 3 взаємодії в навчанні.

Відмінність способів розбиття обов'язково описати в дипломі — результати двох доменів не можна порівнювати між собою напряму.

### Релевантність

Об'єкт у тесті релевантний, якщо `value ≥ 8` (тобто ≥ 4 зірок у MovieLens). Неявні взаємодії Book-Crossing використовуються для навчання, але не вважаються релевантними в тесті.

### Протокол

Для кожного тестового користувача модель отримує його навчальну історію, ранжує **всі** об'єкти домену, яких немає в навчальній історії, і повертає top-K. Ранжування по повному каталогу, без підвибірки негативних прикладів.

Метрики для K ∈ {5, 10, 20}, усереднені по користувачах:

- `Precision@K = |rel ∩ topK| / K`
- `Recall@K = |rel ∩ topK| / |rel|`
- `NDCG@K = DCG@K / IDCG@K`, де `DCG@K = Σᵢ relᵢ / log₂(i + 1)`, релевантність бінарна, `IDCG` — для `min(K, |rel|)` релевантних на перших позиціях.

Додатково (дешево, але посилює роботу): покриття каталогу (частка об'єктів, що хоч раз потрапили в top-10) і окремий зріз метрик для «холодних» користувачів (< 10 взаємодій у навчанні) — саме тут гібрид має показати перевагу.

Метрики покрити юніт-тестами на ручних прикладах із відомою відповіддю.

### Моделі та підбір параметрів

| Модель | Параметри, що підбираються на валідації |
|---|---|
| Популярність | — |
| Контентна | — |
| ALS | `factors` ∈ {32, 64, 128}, `regularization` ∈ {0.01, 0.05, 0.1}, `iterations` ∈ {15, 30} |
| Гібрид (зважений) | `α_max` ∈ {0.3, 0.5, 0.7, 0.9}, `n_full` ∈ {10, 20, 40} |
| Гібрид (RRF) | — |
| Гібрид + LLM | — |

Критерій вибору — NDCG@10 на валідації. Фінальні числа рахуються на тесті один раз, моделлю, навченою на навчанні + валідації.

**LLM-переранжування** оцінюється на випадковій підвибірці 200 тестових користувачів (`seed=42`): гібрид дає top-30, LLM обирає top-10, метрики рахуються для K ∈ {5, 10}. Для чесності гібрид без LLM рахується на тій самій підвибірці. Відповіді моделі кешуються на диску, щоб експеримент можна було перезапустити. Варто очікувати, що LLM не обов'язково покращить метрики точності — його головна цінність у поясненнях; будь-який результат слід подавати як є.

### Результати

`artifacts/eval/{domain}_{дата}.csv` (модель, K, метрика, значення, кількість користувачів), `{domain}_params.json` (обрані гіперпараметри), графіки PNG (matplotlib: стовпчики NDCG@10 за моделями; лінії метрик за K). Також друкується Markdown-таблиця для вставки в текст диплома.

## 11 Відомі пастки

- **`implicit` на Windows** без компілятора не встановлюється. Увесь Python запускається тільки в контейнері (Linux, Python 3.11 — для нього є готові збірки). Готовим збіркам потрібна бібліотека OpenMP `libgomp1` — вона вже встановлюється в `backend/Dockerfile`; без неї `import implicit` падає з `libgomp.so.1: cannot open shared object file`.
- **`implicit` ≥ 0.5** очікує матрицю `user × item` (у старих прикладах з інтернету — навпаки). Перевірити за документацією встановленої версії.
- **Розмірність вектора** в БД (1024) має збігатися з моделлю ембедингів. Зміна моделі = нова міграція + перерахунок.
- **pgvector і SQLAlchemy**: використовувати пакет `pgvector` (`from pgvector.sqlalchemy import Vector`); драйвер — `psycopg` 3.
- **Перший запит до Ollama повільний** (модель вантажиться в пам'ять). Задати змінну середовища хоста `OLLAMA_KEEP_ALIVE=30m`. Дві моделі одночасно (`qwen3:8b` + `bge-m3`) на 8 ГБ VRAM уміщуються впритул; ембединги рахуються офлайн, тож онлайн потрібна лише одна.
- **Кодування Book-Crossing** — latin-1, не UTF-8; HTML-сутності в назвах (`&amp;`) слід розкодувати.
- **Витік даних в оцінюванні**: ALS для експериментів навчається лише на навчальній частині. Артефакти для вебзастосунку (навчені на всіх даних) і для експериментів — це різні файли.
- **Контекст LLM**: 30 кандидатів з описами + профіль мають уміщатися в `num_ctx`. Якщо промпт довший за ~6000 токенів — скоротити описи, а не збільшувати контекст.
- **Docker Desktop + довга кирилична назва теки**: bind-монтування падає з `file name too long` (обмеження 255 байт на компонент шляху в Linux). Тому проєкт використовує лише іменовані томи та `docker compose watch` (розділ 02). Не додавати `./щось:/app/...` у `docker-compose.yml`.
- **Код у контейнері `api` без `watch` не оновлюється**: після змін у `backend/` або тримати запущеним `docker compose watch`, або виконати `docker compose up -d --build api` перед `exec`-командами й тестами.
- **Попередження `StarletteDeprecationWarning` про `httpx`** у pytest іде з самої FastAPI/Starlette — ігнорувати, доки FastAPI не оновить `TestClient`.
